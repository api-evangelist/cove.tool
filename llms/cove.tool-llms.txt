# cove.tool

> cove.tool (the company rebranded to "cove" in January 2025) is an Atlanta, Georgia
> building-performance analysis platform for architects, engineers and contractors. Its
> analysis.tool engine runs energy, daylight, glare, embodied carbon, water, radiation, shadow and
> cost-versus-performance optimization on early-stage building designs. The public REST API,
> marketed as api.tool, lets a program create projects, upload building geometry, pick an energy
> code, start simulations, poll job status and read EUI, sDA and ASE results without touching the
> web application.

## Before you call anything

- You need a valid trial or licensed cove.tool account. There is no self-serve API tier and no
  published pricing; the api.tool product routes to a demo request.
- Mint a token: `POST https://app.covetool.com/api/get-token` with account credentials.
- Send it on every request as `Authorization: Token <api_token>`. The scheme word is `Token`, not
  `Bearer` — a live 401 answers `www-authenticate: Token`.
- Base URL, current version: `https://app.covetool.com/api/v2`
- Every response wraps the payload: `{"data": ..., "msg": ..., "errors": [...]}`. Unwrap `.data`.

## Operations — v2, base https://app.covetool.com/api/v2

Neither specification declares an operationId. The names below are assigned by
overlays/cove.tool-rest-api-v2-overlay.yaml; the method and path are the provider's.

- `POST /auth/signup` — create a cove.tool user account on your organization's license. The only
  operation on the surface that declares no security.
- `GET /profiles/{profile_id}` — read a user account inside your business. 403 if outside it.
- `GET /energy-codes` — list supported energy codes. Query `for_project` to get only the codes
  compatible with a project, `name` to filter by name.
- `POST /projects/` — create a project. Requires `name`, `location` ("34.177114, -86.830390"),
  `building_types` (e.g. ["Office","Retail"]) and `energy_code_id`.
- `GET /projects/?project_id=` — read one project.
- `PUT /projects/{project_id}` — update a project.
- `POST /projects/{project_id}/geometry` — upload the building model. Requires `floors`, `walls`,
  `windows`, `roofs`, `floor_area`, `roof_area`, `ground_floor_area`, `building_height`,
  `si_units`, AND at least one non-zero value across the eight `wall_area_*` and eight
  `window_area_*` cardinal-direction fields. Missing that last condition is the usual cause of a 400.
- `POST /analysis` — start simulation. Requires `project_id` and `analysis_types` (e.g.
  ["daylight"]). Returns 202 Accepted; results are not in the response.
- `GET /analysis/{project_id}/status` — remaining jobs per analysis type. Poll this.
- `GET /analysis/{project_id}` — fetch daylight results as per-room meshes.
- `GET /analysis/{project_id}/stop` — halt running calculations. Note this is a GET that mutates
  state; do not let a crawler, cache or speculative agent touch this URL.

## Operations — v1, base https://app.covetool.com/api

- `POST /get-token` — obtain an API token.
- `GET /projects` — list all projects. No pagination parameters exist; the response is unbounded.
- `POST /run-values` — update geometry values for a project/run. Superseded in v2 by
  `POST /projects/{project_id}/geometry`.

## How a run actually goes

1. `GET /energy-codes` — pick an `energy_code_id`.
2. `POST /projects/` with name, location, building_types, energy_code_id — keep the returned `id`.
3. `POST /projects/{project_id}/geometry` with areas and surfaces.
4. `POST /analysis` with `{project_id, analysis_types}` — expect 202.
5. Poll `GET /analysis/{project_id}/status` until the remaining job count for your analysis type
   reaches zero.
6. `GET /analysis/{project_id}` for results.

There are no webhooks and no callbacks. Polling is the only completion signal.

## Things an agent must know that the docs do not say

- **No idempotency.** `POST /analysis` enqueues billable simulation work and supports no
  Idempotency-Key. If a request times out, you cannot safely retry it — check status first.
- **No rate-limit headers.** No `RateLimit-*`, no `X-RateLimit-*`, no `Retry-After`, and no 429
  declared in either spec. You cannot back off on a signal; you can only be refused. The only
  consumption ceiling is the per-project remaining-jobs count from the status endpoint.
- **Trace every failure.** Responses carry an undocumented `x-cove-unique-trace-id` header of the
  shape `<uuid>-<unix-timestamp>`, emitted even on 401. Capture it and quote it to support.
- **Error bodies do not match the contract.** The spec declares `{data, msg, errors}` but the live
  401 returns Django REST Framework's `{"detail": "..."}`. Handle both.
- **No 5xx is declared** on any operation, so a generated client has no typed path for server
  failure.
- **`cebcs_eui` vs `cbecs_eui`.** The project schema's `required` list names a field the schema
  never defines. Do not assume `cbecs_eui` will be present.

## Status, security and support

- No status page. status.covetool.com and status.cove.tools do not resolve;
  covetool.statuspage.io is Atlassian's generic marketing page, not cove.tool's.
- No security.txt, no OpenID configuration, no OAuth metadata, no ai-plugin.json, no agent card —
  every `/.well-known/` path 404s on the API and docs hosts.
- No MCP server.
- No first-party SDK on npm, PyPI or anywhere else. cove.tool's own advice is to use HTTPie or
  Postman. The Revit / Rhino / Grasshopper / SketchUp plugins are end-user CAD plugins, not client
  libraries.
- Support is an Intercom help center: https://help.covetool.com/en/
